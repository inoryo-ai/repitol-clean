## 1. このプロジェクトで「正しい結果」とは何か

### プロダクト概要
飲食店がLINE公式アカウントと連携し、顧客管理・クーポン配信・予約リマインド・デジタルスタンプカードを月額980円から使えるCRM SaaS。

### 正しい結果の具体例

- **正しい結果1**: 来店客がQRコードを読み取ってLINE友だち追加 → 自動で顧客DBに登録。名前・来店日時・初回来店フラグが記録される
- **正しい結果2**: 来店3回目の顧客に「常連限定クーポン（ドリンク1杯無料）」がLINEで自動配信される。顧客がクーポンを店頭で見せ、使用済みに変更 → 再利用不可になる
- **正しい結果3**: 予約を入れた顧客に、予約日前日の18:00にLINEで自動リマインドが届く。「明日19:00にご予約いただいています。お待ちしております！」
- **正しい結果4**: スタンプカード機能でスタッフが「スタンプ付与」ボタンを押す → 顧客のLINEに「スタンプ5/10個目！」と通知 → 10個で特典クーポンが自動発行
- **正しい結果5**: 店長が管理画面で「過去30日来店なし」の顧客セグメントを作成 → そのセグメントに「お久しぶりクーポン」を一斉配信

---

## 2. 「間違った結果」の具体例

- **間違い1**: 同じ顧客が二重登録される（LINE IDで一意管理されていない）
- **間違い2**: 使用済みクーポンが再度使える（クーポン無効化が失敗）
- **間違い3**: 予約リマインドが予約時刻の後に届く
- **間違い4**: セグメント「常連」に1回しか来ていない顧客が含まれる
- **間違い5**: 他店舗の顧客データが見える（マルチテナント分離の失敗）
- **間違い6**: LINE配信数がLINE公式の無料枠を超えて店舗に予想外の請求が発生（通知なし）
- **間違い7**: スタンプが来店なしに勝手に増える（不正付与）

## 4. ユーザーの行動想定

### ユーザーA: 飲食店オーナー（小規模・個人経営）

- **誰か**: 居酒屋・カフェ・ラーメン店等の個人オーナー（30〜50代、ITリテラシー低〜中）
- **典型的な行動パターン**:
  1. LINE公式アカウントは作ったがメッセージ一斉配信しかしていない
  2. 常連客の名前は覚えているが、データとしては管理していない
  3. クーポンは紙で配っている or 何もしていない
  4. 「リピーターを増やしたいがやり方がわからない」
- **期待すること**: 難しい設定なしで使いたい。スマホだけで全部できてほしい
- **絶対にやってほしくないこと**: 複雑なUI、高額請求、顧客データの漏洩

### ユーザーB: 飲食店スタッフ

- **誰か**: アルバイト・パートスタッフ（20代〜、ITリテラシー中）
- **典型的な行動パターン**:
  1. 会計時に「LINE友だち追加でドリンク1杯サービス」と案内
  2. スタンプ付与ボタンを押す
  3. 予約を手入力する
- **期待すること**: 1タップで完了する操作。研修不要で使える
- **絶対にやってほしくないこと**: オペレーションの負担が増えること

### ユーザーC: 来店客（飲食店の顧客）

- **誰か**: 飲食店の一般客（全年齢）
- **典型的な行動パターン**:
  1. 会計時にQRコードを読み取ってLINE友だち追加
  2. クーポンがLINEに届く → 次回来店時に提示
  3. スタンプが貯まると特典がもらえる
- **期待すること**: うざくない頻度の通知。お得なクーポン
- **絶対にやってほしくないこと**: 毎日通知が来る。個人情報を聞かれる

## 5. 品質基準（定量）

| 指標 | 合格ライン | 測定方法 |
|------|----------|---------|
| 友だち追加→顧客登録の成功率 | 99%以上 | Webhook受信ログ |
| クーポン配信→到達率 | 99%以上 | LINE API送信ログ |
| 予約リマインド送信精度 | 100%（送り忘れゼロ） | cronジョブログ |
| 管理画面の操作完了時間（クーポン作成） | 3分以内 | 実操作テスト |
| スマホでの管理画面操作性 | 全機能がスマホで完結 | 実機テスト |
| 顧客データの二重登録率 | 0% | LINE IDユニーク制約 |
| LINE配信数の超過警告 | 80%到達時に通知 | 配信数カウント |

## 6. 前提条件

| 前提 | 崩れた場合の影響 | 代替策 |
|------|---------------|--------|
| 飲食店がLINE公式アカウントを持っている | 当SaaSの前提が崩れる | 公式アカウント作成をオンボーディングに組み込む |
| LINE Messaging APIのWebhookが安定動作する | 友だち追加・メッセージ受信が機能しない | リトライ機構を実装 |
| 顧客がLINEを使っている | ターゲット顧客にリーチできない | 日本のLINE利用率95%なのでリスク低 |
| Supabase無料枠で初期運用可能 | 月額コスト発生 | 無料枠内に収まる設計 |
| Vercel無料枠でホスティング可能 | ホスティングコスト発生 | 初期は無料枠で十分 |

## 7. MVP機能一覧

### 必須（MVP）

| # | 機能 | 説明 |
|---|------|------|
| 1 | 店舗アカウント認証 | メール+パスワード。LINE公式アカウントとの連携設定 |
| 2 | LINE Webhook受信 | 友だち追加・メッセージ受信・フォローイベントの処理 |
| 3 | 顧客管理 | LINE友だち追加で自動登録。来店回数・最終来店日・メモの管理 |
| 4 | 来店記録 | スタッフがスマホで「来店チェックイン」→ 来店回数+1 |
| 5 | クーポン作成・配信 | テキスト+画像のクーポン作成。手動一斉配信 or セグメント配信 |
| 6 | 自動クーポン配信 | 条件トリガー（初回来店お礼/N回来店特典/N日未来店の呼び戻し） |
| 7 | デジタルスタンプカード | 来店ごとにスタンプ付与。N個で特典クーポン自動発行 |
| 8 | 予約管理+リマインド | 簡易予約登録。前日にLINEリマインド自動送信 |
| 9 | セグメント機能 | 来店回数・最終来店日・タグで顧客を分類。セグメント別配信 |
| 10 | 配信数モニタリング | LINE配信数のカウント・残量表示・80%到達時の警告 |
| 11 | 管理者ダッシュボード | 友だち数・来店数・クーポン使用率・リピート率の可視化 |

### 後回し（v2以降）

| 機能 | 理由 |
|------|------|
| リッチメニュー自動設定 | LINE API側の制約が複雑 |
| ポイント制（金額ベース） | スタンプカードで代替可能 |
| 複数店舗管理 | MVPは1店舗から |
| 食べログ/ホットペッパー連携 | API公開状況次第 |
| 顧客アンケート機能 | v2で追加 |

## 8. 技術スタック

| レイヤー | 技術 | 理由 |
|---------|------|------|
| フロントエンド | Next.js 16 / React 19 | ケアログと同じ技術基盤で開発効率最大化 |
| UI | shadcn/ui + Tailwind CSS 4 | 同上 |
| バックエンド | Next.js API Routes | 同上 |
| データベース | Supabase（PostgreSQL） | 無料枠あり。RLS対応 |
| 認証 | Supabase Auth | 同上 |
| LINE連携 | LINE Messaging API | Webhook受信 + Push配信 |
| 予約リマインド | Vercel Cron or 外部cron | 毎日18:00に翌日予約をチェック→送信 |
| ホスティング | Vercel | 無料枠で運用 |

## 10. 競合との差別化

| 競合 | 月額 | 弱点 | 当SaaSの差別化 |
|------|------|------|---------------|
| Lステップ | 2,980円〜 | 高機能だが高額・設定が複雑 | 飲食店に特化してシンプル。980円から |
| エルメ | 0円〜 | 無料枠あるがCRM機能が弱い | 顧客管理+スタンプカードが標準装備 |
| LINE公式の標準機能 | 0円 | セグメント配信・自動配信が弱い | 来店回数ベースの自動配信 |
| リザービア | 10,000円〜 | 予約特化で高額 | 予約+CRM+クーポンが一体で980円 |

**差別化ポイント: 「飲食店専用。月980円でリピーターが増える」**
